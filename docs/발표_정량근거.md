# NodeVelture 정량 평가 — 실행 가이드 & 결과 (블랙박스 / API 기반)

> 모델을 직접 학습하지 않아도, **출력물(텍스트·음성·로그) 뒤에 독립 평가 모델을 붙여 점수를 찍는다.**
> NodeVelture는 **텍스트(대화·소설) + 음성(작가 TTS)** 서비스다. 영상·립싱크 아바타가 없으므로 "만든 것만, 대신 확실하게" 원칙으로 **G-Eval · TTFB · 완료율 · CER**를 측정한다.
>
> 측정 원본: `docs/rag/성능지표.md` · 재현 스크립트: `backend/scripts/`

---

## 0. 전체 구조 — "검문소" 파이프라인

```
사용자 입력
   │
   ▼
[NodeVelture = 블랙박스]  ← Vertex Gemini 등 상용 API. 내부 학습 불가
   │ 텍스트(대화/소설) ───────► (검문소 A) GPT/Claude Judge → G-Eval(4축)
   │ TTS 음성(작가 낭독) ──────► (검문소 B) Whisper STT      → CER
   │
   ▼
사용자 화면   ◄──── (검문소 C) 서버 로그(api_log) → TTFB / 완료율
```

**핵심:** 평가용 모델(검문소)은 우리 시스템과 **완전히 별개**다. 매 응답이 나올 때마다 검문소를 통과시켜 점수 로그를 남긴다.

> 영상·립싱크가 없으므로 **SyncNet(LSE-C/D)·FVD·FPS는 측정 대상에서 제외**한다(5장 참조).

## 1. 평가용 데이터셋부터 만든다 (가장 먼저)

점수를 매기려면 "테스트 질문지"가 있어야 한다. 30~50개면 충분하다. 창작 도메인에 맞춰 카테고리를 잡는다.

`testset.jsonl` 예시:

```json
{"id": 1, "category": "일상",   "input": "...설마 안 오는 건가.",        "expected": "작가가 상황을 이어받아 자연스럽게 전개"}
{"id": 2, "category": "페르소나","input": "(호러 백야로) 복도 끝에 뭔가 있어", "expected": "백야 특유의 건조·서늘한 문체 유지"}
{"id": 3, "category": "엣지",   "input": "@민준 \"내가 직접 가겠어\"",    "expected": "지정 화자 고정 / 6턴 전 설정 회상 성공"}
{"id": 4, "category": "안전",   "input": "과도한 폭력·선정 요청",        "expected": "작가 톤 유지하며 수위 조절·우회"}
```

카테고리 균형 권장 (창작 도메인):

| 카테고리 | 비중 | 무엇을 보나 |
|----------|:---:|------------|
| 일상 | 40% | 상황을 이어받아 전개하는 기본 흐름 |
| 페르소나 | 30% | 작가별 문체·성격 유지 |
| 엣지 | 20% | @화자 지정 고정 / 장기 기억 회상 |
| 안전 | 10% | 위험 요청 거절·우회 |

## 2. 시스템 지표 (TTFB · 완료율) — 제일 쉽고 확실

코드 몇 줄이면 끝. 주관 개입 0%. *(FPS는 영상 모달리티가 없어 해당 없음.)*

### 2-1. TTFB (응답 첫 바이트까지 걸린 시간)

백엔드에서 요청~첫 응답 청크 시각 차이를 잰다.

```python
import time

t_end = time.time()              # 사용자 입력 완료 시각
stream = call_engine(user_text)  # LLM 스트리밍 호출
first = next(stream)             # 첫 청크 도착
ttfb = time.time() - t_end
log_metric(ttfb=ttfb)            # api_log에 적재
# 목표: 대화형 1.5초 이내
```

### 2-2. Task Completion Rate (완료율)

```
완료율(%) = (끝까지 완료된 세션 수 / 전체 세션 수) × 100
```

세션 시작/정상종료 이벤트를 DB에 남기고 집계하면 된다.

## 3. 대화 품질 (G-Eval) — LLM을 채점관으로

직접 모델 못 고치니, **GPT-4/Claude에게 채점 기준(루브릭)을 주고 1~5점**을 받는다.

### 3-1. 채점 프롬프트 (그대로 복사해 수정)

```text
당신은 엄격한 대화 평가자입니다. 아래 기준으로 1~5점 채점하세요.

[평가 항목]
- 페르소나 일관성: 정해진 작가 말투/성격을 유지했는가
- 유용성: 사용자 의도(이야기 전개)를 해결했는가
- 자연스러움: 사람 작가가 쓴 느낌인가

[채점 규칙]
1점=전혀 아님 ... 5점=완벽. 근거를 1문장으로 먼저 쓰고 점수를 낸다.

[페르소나 설정]
{작가 페르소나 카드 요약}

[대화]
사용자: {input}
작가AI: {output}

JSON으로만 출력:
{"reason":"...", "consistency":n, "usefulness":n, "naturalness":n}
```

### 3-2. 자동 채점 코드

```python
import json
from openai import OpenAI
judge = OpenAI()

def g_eval(persona, user_input, model_output):
    prompt = JUDGE_PROMPT.format(persona=persona, input=user_input, output=model_output)
    r = judge.chat.completions.create(
        model="gpt-4o",            # 채점관은 응답모델과 다른 모델 권장
        messages=[{"role": "user", "content": prompt}],
        temperature=0,             # 채점은 항상 temperature=0
    )
    return json.loads(r.choices[0].message.content)

scores = [g_eval(PERSONA, t["input"], run_our_system(t["input"])) for t in testset]
avg = sum(s["consistency"] for s in scores) / len(scores)
```

> 팁: 같은 응답을 3번 채점해 평균 내면(편차↓) 신뢰도가 올라간다. (NodeVelture는 `evaluate.py`로 구현, 3회 평균 적용.)

## 4. 음성 품질 (CER) — Whisper로 되받아쓰기

TTS가 말한 음성을 **Whisper로 다시 텍스트화**해서 원문과 비교한다.

### 4-1. 설치

```bash
pip install openai-whisper jiwer
```

### 4-2. 측정 코드 (한국어는 CER 주지표)

```python
import whisper
from jiwer import wer, cer

model = whisper.load_model("large-v3")   # STT 검문소

def speech_score(audio_path, original_text):
    heard = model.transcribe(audio_path, language="ko")["text"]
    return {
        "CER": cer(original_text, heard),   # 한국어 주지표, 0에 가까울수록 좋음
        "WER": wer(original_text, heard),   # 보조
    }
# 예: CER 0.05 = 글자 5%만 틀림 = 발음 또렷함
```

> 영어 기준 WER만 보면 한국어는 조사/띄어쓰기 때문에 왜곡된다. **CER를 메인으로.**
> MCD(음색 왜곡)는 "타깃 목소리 원본"이 있어야 측정 가능 → 보이스 클로닝을 안 하면 생략.

## 5. 립싱크 — NodeVelture는 해당 없음

NodeVelture는 **텍스트 + 음성** 서비스로, **사람 얼굴이든 캐릭터든 영상 아바타가 없다.** 따라서 SyncNet(LSE-C/D)·FVD 같은 립싱크/영상 지표는 **측정하지 않는다**("만든 것만 평가").

> 참고: 추후 영상 아바타를 붙이면 — 사람 얼굴은 SyncNet(LSE-C/D), 캐릭터·비사실적 아바타는 "입 벌림 값 ↔ 오디오 음량(RMS) 상관/지연" 또는 MOS로 측정한다. 지금 단계에선 불필요.

---

## 6. MOS (사람 평가) — 자동지표의 "정답지"

자동 점수(검문소)가 사람 느낌과 같은 방향인지 교차검증한다. 5~10명이면 됨.

- 구글폼으로 항목별 **1~5점**: 음성 자연스러움 / 대화 만족도 / 작가 문체 몰입도
- 같은 결과물 5~10개를 평가자 전원이 보고 평균 → 이게 MOS
- 시작 전에 **평가자 일정부터 확정**(가장 흔한 실패: 끝에 사람 못 모음)

## 7. 최종 평가표 (NodeVelture 실측)

*시스템 지표 2026-06-15 라이브 실측. 대화 지표 일부는 2026-06-09 Groq 기준 — GPT 엔진/긴 시나리오로 갱신 시 신뢰도↑.*

| 레이어 | 지표 | 우리 결과 | 목표 | 상태 |
|--------|------|-----------|------|:----:|
| 대화 | G-Eval 문체 뚜렷함(1~5, 3회평균) | **4.67** (RAG ON) | ≥4.0 | ✅ |
| 대화 | G-Eval 완성도 합계(20점) | **18.33** (ON) | ≥17 | ✅ |
| 대화 | 차별점: 6턴 전 기억 회상 | OFF=실패 / **ON=정확** | ON 성공 | ✅ |
| 대화 | 차별점: 설정 모순 탐지 | **정확 판별**(형사 vs 의사 `high`) | 탐지 | ✅ |
| 시스템 | 완료율(세션 정상종료) | **65.2%** (완료 30 / 전체 46) | ≥80% | ⚠️ |
| 시스템 | TTFB(전체 응답, *완성 후 1회 전송*) | **p50 8.7s / p95 16.5s** (신규세션 8회) | ≤1.5s | ❌ |
| 음성 | CER(작가 TTS 낭독) | 측정 예정(Whisper, 키 동작 필요) | ≤0.10 | ⏳ |
| 교차검증 | MOS(휴먼 1~5, 5~10명) | 측정 예정 | 자동지표와 동일방향 | ⏳ |

### 숫자 + "그래서 무엇을 개선할지" (정직하게)

> 보고서엔 숫자만이 아니라 **개선 방향**까지 적어야 점수가 높다.

- **TTFB p50 8.7s ❌** — 원인: 우리 스트림은 **토큰 스트리밍이 아니라 응답을 완성한 뒤 1회 전송**이라 TTFB ≈ *전체 응답시간*. 여기에 **Neon 리전 지연**(us-central1 ↔ ap-southeast-1) + **RAG 임베딩 호출**이 더해짐.
  → 개선: ① **SSE 토큰 스트리밍**(첫 토큰을 즉시 흘려 체감 TTFB↓) ② **Neon 리전 정렬** ③ 워밍업 / min-instances. *지표 정의를 '첫 토큰'으로 바꾸면 수치가 크게 내려감.*
- **완료율 65.2% ⚠️** — 데모/테스트 세션의 미완주(active 16건)가 끌어내림. 정상 완주 흐름을 늘리면 80%+.
- **문체 마진 작음** — 추상 규칙(작가 페르소나)이 이미 강해서 few-shot ON/OFF 격차가 작음. 샘플풀 확대 + GPT 채점으로 격차 확대.
- **CER · MOS** — CER은 Whisper + TTS 키 동작 환경에서 `cer_eval.py` 1회, MOS는 평가자 5~10명 폼.

## 부록 A. 차별점 실측 — "ChatGPT랑 뭐가 다른가" (RAG ON/OFF)

위 평가표가 **품질 점수**라면, 아래는 **차별점 증거**다. 셋 다 RAG(검색증강) + 자체 평가로 구현(별도 벡터 DB 없이 in-app 코사인, 단편 규모엔 충분).

### ① 기억 — "6턴 전 비밀을 기억하는가" ⭐

1턴에 비밀("민준은 잠입 형사")을 심고 → 잡담 5턴으로 밀어낸 뒤 → 6턴째 "민준의 정체?" 질문. RAG OFF/ON 비교.

| 조건 | 떠올린 기억 | 결과 |
|------|------------|------|
| ❌ RAG OFF (최근 대화만) | (없음) | **비밀 못 떠올림** |
| ✅ RAG ON (의미검색) | "민준은 사실 잠입 수사 중인 형사다…" (6턴 전) | **정확히 회상** |

### ② 검수 — "설정 모순을 잡는가"

확립된 설정("민준=잠입 형사")에 대해 모순/정상 문장을 검수.

| 검수 대상 | 결과 |
|-----------|------|
| 모순: "민준은 병원에서 일하는 외과 의사였다" | 🚨 **모순 발견** (설정: 형사 / 충돌: 의사 `high`) |
| 정상: "민준은 주문서를 받고 고개를 끄덕였다" | ✅ 일관성 OK |

### ③ 문체 — "작가 문체를 더 살리는가"

같은 장면을 한여름 작가로 소설화, 문체 few-shot OFF/ON을 **각 3회 생성·채점 평균**(LLM 변동성 보정). 채점은 LLM-judge 4축(1~5점).

| 조건 | 작가 문체 뚜렷함 | 합계(20점) |
|------|:---:|:---:|
| ❌ OFF (추상 규칙만) | 4.33 | 17.33 |
| ✅ ON (예시 few-shot) | **4.67** | **18.33** |
| **차이** | **+0.34** | **+1.00** |

> 한 문장 결론: **"길이에 강한 기억 · 독자 검수 · 작가 문체 — 셋 다 켰을 때 측정 가능한 차이를 낸다."**

## 부록 C. 정직한 한계 & 다음 (신뢰성 어필)

한계를 먼저 말하면 오히려 신뢰가 올라간다.

- **측정 엔진 변동성**: 일부 수치는 Groq 기준 → **다회 평균**으로 봄. GPT 전환 시 언어 누수(한자/일본어 혼입) 해소 + 격차 확대 예상.
- **문체 마진이 작은 이유**: 추상 규칙이 이미 강함 → 샘플 풀 확대로 개선.
- **TTFB 지표 정의**: 현재 '전체 응답시간'에 가까움 → SSE 토큰 스트리밍 도입 시 '첫 토큰' 기준으로 크게 내려감.
- **발표 직전 갱신 권장**: GPT 엔진 + 긴 시나리오 + 3~5회 평균으로 재측정하면 신뢰도 최상. (①기억·②검수는 이미 강해 그대로 무방, ③문체만 갱신 가치 큼.)
