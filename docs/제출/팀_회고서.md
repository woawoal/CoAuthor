## 프로젝트 한 줄 요약
사용자가 작가에 "빙의"해 캐릭터와 놀듯 대화하다 **진짜 내 소설**로 완성하는 AI 협업 창작 서비스. FastAPI(Cloud Run) + React/Vite(Vercel) + Vertex Gemini + RAG 3종 + 멀티모달(삽화·음성).

## 잘된 점 (협업)

1. **역할 분담 → 기능 담당제로 유연하게 전환** — 처음엔 백엔드/프론트/AI로 **역할을 나눠 시작**했지만, 프로젝트를 진행하면서 **각자 기능을 맡아 끝까지(백엔드~프론트~배포) 책임지는 '기능 담당제'**로 자연스럽게 바뀌었다. 경계에 얽매이지 않고 필요한 곳을 메워 속도가 붙었고, 그 와중에도 `dev` 보호(전원 1승인 머지)로 메인 안정성은 지켰다.
2. **차별점을 수치로 증명** — RAG ON/OFF(기억·검수·문체), G-Eval·CER·TTFB·완료율을 측정·문서화해 "ChatGPT와 뭐가 다른가"에 근거로 답할 수 있게 됨.
3. **멀티모달을 끝까지 붙임** — 텍스트뿐 아니라 삽화(Vertex Gemini Image)·음성(작가 리액션 TTS)까지 실제 동작하는 데모를 완성.
4. **배포 함정 공유** — Cloud Run env/시크릿, Vercel Production 승격 등 반복 함정을 `server-ops.md` 체크리스트로 정리해 팀 전체가 같은 실수를 반복하지 않게 함.

## 개선점

1. **초기 설계·창작 도메인 정의 부족** — 아키텍처 구조와 "**소설은 실제로 어떻게 쓰이는가**"라는 창작 도메인 자체를 처음에 깊이 합의하지 못한 채 기능부터 붙여나갔다. 그러다 보니 대화→소설 변환이라는 핵심 흐름, 데이터 모델(세계관·인물·기억), 화면 구조가 중간에 여러 번 갈아엎였다. → 착수 전에 **창작 프로세스 모델링 → 데이터/화면 설계 합의**를 먼저 끝내고 구현에 들어갔어야 한다. 도메인을 먼저 이해했다면 재작업과 충돌이 크게 줄었을 것.
2. **머지 충돌** — 같은 파일(예: `chat/ui.jsx`)을 여러 명이 동시에 손대 충돌이 잦았다. → 작업 단위를 더 잘게 쪼개고, 겹치는 영역은 사전 공유. (위 1번처럼 설계가 선행됐다면 경계가 분명해져 충돌도 줄었을 것.)
3. **수동 배포** — Cloud Run을 매번 수동(gcloud)으로 올려 누락·지연이 있었다. → CI/CD(자동 배포) 또는 배포 담당·절차 고정.
4. **배포 환경변수 누락 반복** — 새 API 키/주소가 클라우드에 안 올라가 장애가 반복됐다. → 체크리스트로 보완했으나, 환경변수 관리 자동화가 필요.
5. **성능(TTFB)** — 응답을 "완성 후 1회 전송"하던 초기 구조라 체감 지연이 컸다. → SSE 토큰 스트리밍 **백/프 배포 완료**(첫 토큰 ~1-2s 체감), Neon 리전 정렬은 다음 과제.
6. **테스트 커버리지** — 핵심 흐름 자동 테스트가 부족. 출시 전 점검을 수동 e2e로 메움.
