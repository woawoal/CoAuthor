# 최종 발표 피드백 — NodeVelture (1팀 woawoal)

> AI휴먼 캠프 4기 · 최종 발표(2026-06-19)에서 받은 심사위원·튜터 피드백 정리.
> 칭찬 → 질의응답 → 아쉬운 점/개선 제안 → 튜터 피드백 순. 회고·차기 개선의 근거 자료.

---

## 1. 잘된 점 (칭찬)

- **주제 선정 기획이 굉장히 좋았다.**
- **PPT 디자인 통일성**이 깔끔하게 보였고, **스토리텔링이 잘 되어 있었다.**
- 발표 **시간을 지키려고 말을 빨리한 점** — (의도가 보여) 칭찬.
- **서비스/오탈자 체크가 실제로 반영된 점**을 보아 좋았다.
- **UI/UX 퀄리티가 높아 보인다.** 실제 서비스 같은 디테일이 있어 이 부분은 아주 잘했다. *(튜터)*

## 2. 질의응답 (발표 중 받은 질문)

### Q. 폴백(fallback)이 있던데, 소설을 작성하다 Groq으로 넘어가면 로직이 그대로 적용되나?
- **A.** API가 불리기 전에 **이미 데이터를 저장해 놓기 때문에 응답 엔진과는 상관이 없다.**

### Q. 그래도 첫 문단을 쓰다가 폴백을 타고 가면, 응답 엔진에 따라 답변이 달라지지 않는가?
- **A.** **고정 데이터(세계관·설정 등)를 가져오기 때문에 괜찮다고 판단**한다.
  - ⚠️ **솔직한 한계:** 이에 대한 **실험 결과는 아직 없음** → 차기 과제로 폴백 전/후 출력 일관성 검증 필요.

## 3. 아쉬운 점 · 개선 제안 (심사위원)

### 3-1. 데모 / 영상
- **영상 녹화 툴이 클로닝된 느낌이어서 아쉬웠다.** 오캠(oCam) 같은 툴을 썼다면 품질이 더 좋았을 것.
- 데모에서 **가은님이 짧게 보여주려 했는데, 사용자 입력에 따라 설계를 다 해두었다** — (자유 입력 데모가 아니라 짜인 흐름이라) 아쉬움.

### 3-2. 기능 (구현/역할)
- "작가에게 물어보면 — 중간중간 내가 놓친 게 있는지 물어보면 — **캐릭터가 RAG로 답해주는 기능**"이 **구현이 안 된 것 같다.**
- **아바타가 있긴 하지만 역할이 '피드백'에 그치는 점**이 아쉽다.

### 3-3. 비교 / 근거 (설득력)
- **타 서비스와 비교한 자료가 없는 게 아쉽다.** "다른 서비스보다 우리가 뛰어나다"거나 **출구조사 경험 같은 데이터**가 있었으면 "괜찮은 시스템"이라는 임팩트가 왔을 것.
- 평가가 **너무 주관적인 것 같다.** 평가 때 **Llama 단일 API로 평가**했는데, **다른 모델도 같이 평가**해서 나왔으면 좋았을 것.
- **평가 데이터 문서가 너무 길다.** *(분량 조절 필요)*
- 디자인이 잘 나와 서비스 완성도는 보여줬지만, **품질에 관한 근거 / "작가가 실제로 등단할 수 있는지"** 가 더 있었으면 좋았을 것.

### 3-4. 서비스 방향성 (의문 & 확장 제안)
- **"현재 아마추어 작가에게 진짜 도움이 될까?" 하는 의문.** 지금은 말을 걸고 답변을 받는 수준 — **한 편을 실제로 만들어 검토를 받아봐야** 알 수 있을 것 같다.
- **장르가 한정될 것 같다.**
- (확장 아이디어) 장르가 웹소설로 되어 있긴 했지만, **아마추어 작가 시점**에서:
  - **여러 명이 관심 주제를 두고 협업**하는 시스템
  - **자기 메모장에서 (글감을) 발굴**해 **소설의 기본 프레임을 잡아주는** 기능
- **휴먼/사람들과 소통**하는 요소가 있으면 더 재미있을 것 같다.
- **취향 프로파일**도 본인이 설문식으로 작성할 수 있겠지만, **사용자의 평소 말투 등을 RAG로 꺼내 주면** '발굴' 관점에서 굉장히 괜찮은 서비스가 될 수 있을 것 같다.

## 4. 튜터님 피드백

### 4-1. 발표 구성 · 스토리텔링 (가장 큰 아쉬움)
- 한 것에 비해 **발표 자료/발표 흐름이 좀 아쉬웠다.**
- 바라보는 문서의 구조로 보자면 — **처음에 배경 설명, "왜 이걸 해야 하는지"부터 설득이 부족**했다.
- **"어떻게 해결되고 있지?" 하는 설득이 많이 없었다.**
- **문제 정의 → 우리는 이렇게 해결한다 → 그 솔루션에 이런 기능을 추가했다** 로 이어지는 **스토리텔링이 하나로 연결되는 것이 부족**했다.

### 4-2. 타겟 고객을 먼저 (목적 제시)
- 초반에 **서비스의 목적 — "누구의 어떤 문제를 해결할 것인가"가 먼저 제시**되면 좋았을 것.
- "아, 소설을 쓰고 싶어 하는 누군가에게 도움을 주려는 서비스구나"가 보이도록 **앞에서 타겟 고객을 딱 잡아주면** 좋았을 것.

### 4-3. '페르소나' 개념을 정확히 (중요)
> 다른 조도 마찬가지인 공통 지적.
- **기획에서 말하는 '페르소나'는 '타겟 고객'을 뜻한다.** 특정 사람을 하나 만들어, **그 사람에게 빙의해 이 서비스를 어떻게 대하느냐** — 이것이 페르소나다.
- AI휴먼을 대상으로 하다 보니 **'AI휴먼의 페르소나'(성격·세계관·정의)와 혼동**한 것 → 이건 **다르게 생각했어야** 한다.
- 문제 정의 단계에서의 **페르소나 = 타겟 고객.** 우리가 넣은 **'페르소나 카드'(작가 4인)는 이것과 다르다**는 점을 잘 이해해야 한다.
- **타겟 고객의 페르소나는 더 구체적으로** 잡는 게 좋다 — 누구나 그 사람 입장에서 불편함을 공감할 수 있도록, **빙의될 정보**를 갖춰 **실제 한 인간을 만드는 식**으로 정의한다. 그렇게 더 구체적으로 잡았으면 하는 아쉬움이 남는다.

### 4-4. UI/UX (칭찬)
- 전반적으로 **UI/UX 퀄리티가 높아 보인다.** 실제 서비스 같은 디테일이 있어 **이 부분은 되게 잘하셨다.**
- 다만 **발표가 짧아서인지, 한 것에 비해 설명이 부족하지 않았나** 하는 아쉬움이 남았다.

## 5. 정리 — 핵심 개선 액션

| 분류 | 받은 지적 | 다음 액션 |
|------|----------|----------|
| **발표 구성** | 배경→문제→해결→기능 스토리텔링 단절 | 첫 장에 **타겟 고객 + 문제 정의**부터, 하나의 흐름으로 재구성 |
| **타겟/페르소나** | '페르소나=타겟 고객' 개념 혼동, 추상적 | 구체적 **타겟 고객 페르소나 1인**을 인간처럼 정의(작가 카드와 분리) |
| **비교 근거** | 타 서비스 비교·사용자 데이터 없음 | **경쟁 서비스 비교표** + 소규모 사용자 검증(출구조사) 추가 |
| **평가 신뢰도** | Llama 단일 심판, 문서 과다 | **다중 심판(GPT·Claude) 앙상블**, 평가 문서 **요약본** 분리 |
| **핵심 가치 증명** | "실제 도움/등단 가능?" 의문 | **한 편 완성 → 외부 검토** 사례로 품질 증명 |
| **기능** | 작가에게 되묻는 RAG 응답·아바타 역할 협소 | 캐릭터 능동 질문(RAG 응답) 구현, 아바타 역할 확장 |
| **데모/영상** | 녹화 품질·짜인 데모 | **오캠 등 고품질 녹화**, 자유 입력 데모 비중↑ |
| **확장 방향** | 발굴·협업·소통 부재 | 메모장 글감 발굴, 말투 RAG, 협업/소셜 요소 검토 |
