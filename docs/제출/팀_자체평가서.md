## 0. 한 줄 자평
풀스택 풀사이클(기획→배포→정량평가)을 완주하고 차별점을 **독립 심판 수치**로 증명했다. 그러나 **휴먼 평가·자동화(CI/CD·테스트)·표본 규모**에서 분명한 한계가 있고, 아래에 솔직히 적고 개선 계획을 명시한다.

---

## 1. 잘된 점 (근거만 — 가산 대상 아님, 짧게)
- RAG 3종(기억·검수·문체) 실동작 + **검수 RAG 화면 노출**(🔍 토글·모순 배너).
- 차별점을 **독립 심판(Llama)** 으로 측정: 기억 검색 top-1 **100%**(방해정보 3개 경쟁), 모순 탐지 **95%**, 개인화 추천 톤 인과(DARK<NONE<WARM, 단조), 페르소나 일관성 82%.
- 멀티모달(삽화 Vertex·음성 TTS) + 토큰 스트리밍 배포.
- 배포 함정을 문서화(`server-ops`)해 팀 전체 시행착오 감소.

---

## 2. 약점 → 근거 → 개선 계획 (★가산 핵심)

### 2-1. 휴먼 평가(MOS) 미실시
- **근거:** 모든 품질 지표를 자동/LLM-judge로만 측정. 자동지표가 *사람 느낌*과 같은 방향인지 교차검증이 0건.
- **개선:** 발표 전 **블라인드 MOS 1회**(평가자 5명 × 샘플 10편, 우리/GPT를 A/B 익명·순서 랜덤, 4축 5점 척도). 목적은 *이기기*가 아니라 **자동지표↔사람 감각의 정합성 확인**. 인프라 불필요, 일정만 확보하면 됨.

### 2-2. TTFB 목표 초과
- **근거:** p50 **5.9s** (목표 1.5s). 초기 구조가 "응답을 완성해 1회 전송"이라 TTFB ≈ 전체 응답시간. Neon 리전(us-central1↔ap-southeast-1) 왕복도 가중.
- **개선:** **토큰 스트리밍(SSE delta) 배포 완료** → 첫 토큰 체감 ~1-2s. 남은 과제는 **Neon 리전 정렬**, 그리고 '첫 토큰' 기준으로 지표 재정의·재측정.

### 2-3. 자동 테스트·CI 부재
- **근거:** 출시 점검을 **수동 e2e + 평가 스크립트**로 메움. 회귀를 자동으로 못 막아 같은 기능(예: 말투 추천)이 여러 번 삭제·복구됨.
- **개선:** 핵심 엔드포인트 **스모크 테스트를 CI에 연결**(헬스·세션·스트림·소설변환). PR 머지 게이트에 포함.

### 2-4. 수동 배포 + 시크릿 누락 반복
- **근거:** Cloud Run을 매번 `gcloud` 수동 배포 → 환경변수/시크릿 누락으로 장애 반복(표준 배포 명령의 `OPENAI_API_KEY` 누락 위험을 발견·문서화).
- **개선:** **CI/CD 파이프라인** + 배포 전 **시크릿 체크리스트 자동 검증**(필수 키 존재·형식). 배포 담당·절차 고정.

### 2-5. 머지 충돌 잦음
- **근거:** 같은 파일(예: `chat/ui.jsx`)을 여러 명이 동시 수정 → 충돌·고스트 커밋.
- **개선:** 작업 단위를 더 잘게, **겹치는 영역 사전 공유**, 기능 담당제 유지, squash→merge-commit 전환으로 이력 정리(일부 적용).

### 2-6. 평가 표본 규모 작음
- **근거:** 균형 40문항(엣지 8·안전 4), 기억/모순 n=12~24. **방향 근거이지 통계적 벤치마크 아님**.
- **개선:** 카테고리당 n 확대 + **반복 측정(3~5회 평균)**. GPT-4o 베이스라인 전환 코드 준비됨(크레딧 충전 시 즉시).

### 2-7. 기억 RAG '응답 반영'이 약함
- **근거:** 검색은 강(top-1 100%)인데 **생성 단계 반영은 +17%p**로 약함(검색≠생성).
- **개선:** 프롬프트 강제·재랭킹·인용 강제로 반영률 개선. "RAG는 추천/검수 층에서 ROI가 크다"는 학습을 설계에 반영.

### 2-8. 프롬프트만으로 못 고치는 모델 한계
- **근거:** 현실 세계관에 판타지 입력 시 변환 품질 저하. 세계관 가드 프롬프트 2회 시도했으나 **모델의 '입력 충실 렌더링' 편향**으로 무효 → 토큰만 늘어 되돌림.
- **개선:** 근본 해결은 **상류 입력 차단**(채팅 장르 감지로 선차단 적용)·**구조적 전처리**. 프롬프트가 만능이 아님을 인정하고 개입 지점을 분리.

### 2-9. 멀티모달 클라우드 제약(TTS)
- **근거:** ElevenLabs 무료플랜이 **클라우드 IP 차단(401)** — 로컬 200 / Cloud Run 401.
- **개선:** 리액션 음성은 **Vercel 서버리스 프록시로 우회**(적용). 나레이션 음성(백엔드 직접 경로)은 미해결 → 프록시 일원화 또는 유료 전환 결정 필요.

## 4. 배운 점 (팀 공통)
- **정직한 평가 설계가 신뢰를 만든다** — 자기채점은 거품을 만든다. 독립 심판·출제 편향 제거(교차 라벨링)·통제 실험으로 재면 수치가 내려가도 *방어 가능한 진짜 값*. "100%"보다 한계를 함께 공개하는 게 점수와 신뢰 모두에 낫다.
- **프롬프트의 한계** — 모델의 강한 편향은 지시만으로 안 꺾인다. 구조적 개입(컨텍스트 제거·상류 차단)이 답일 때가 있다.
- **클라우드의 현실 제약**(IP 차단·키 정책)과 벤더 우회 설계(서버리스 프록시)를 몸으로 배움.
- **자동화 부채는 빨리 갚아야 한다** — 수동 배포·수동 테스트가 반복 사고와 회귀의 근원이었다.
